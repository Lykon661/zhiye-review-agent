## 1. 先统一项目定位和简历口径

一句话：**我围绕自己的期末复习需求，做了一个能依据课程原文讲解、生成笔记、安排练习并保存学习记录的本地复习 Agent，重点解决中文提问检索英文课件，以及综合问题证据覆盖不足的问题。**

面试时优先讲这三个点：

1. **跨语言混合检索**：课程笔记中的双语术语对照支持关键词扩展，Granite 支持多语言语义匹配，两条路径用 RRF 融合。
2. **综合问题的证据覆盖**：拆分子主题和比较维度，分别召回、重排、核对原文、补搜缺项，并重新检查最终提示里的证据。
3. **可诊断的 Agent 执行**：工具白名单、调用上限、行动轨迹、引用校验和持久化状态，让失败可以定位到具体阶段。

## 2. 可以直接练习的项目介绍

### 60 秒版本

> 我的项目叫知页，是一个面向期末复习的本地课程复习 Agent。起点是我复习时经常需要用中文理解英文课件，还要在笔记、原文和题目之间来回切换，所以我把资料上传、笔记生成、课程问答、练习和错题记录做成了一个完整流程。
>
> 技术上使用 Vue 3、FastAPI 和 SQLite，向量检索使用本地 Granite INT8 模型与 Chroma。我重点做的是检索可靠性：结合 FTS5/BM25 和向量召回，用 RRF 融合；对列举、对比类问题，拆分子主题和维度，检查课程原文是否真正进入最终提示。
>
> Agent 会根据问题和工具结果决定是否继续检索，程序负责限制工具、范围和重试。我也建立了 30 例数据结构诊断集。已有运行的动作完成率是 93.3%，但我会把流程完成、证据覆盖和回答正确性分开评价，后续改动也需要重新评测。

### 约 3 分钟版本

> 这个项目来自我的真实复习需求。课程资料有英文 PPT、代码、公式和历年试卷，普通问答很容易给出通用教材答案，却不一定符合老师的课件口径。我希望它能围绕当前课程回答，必要时回到具体原文，并把笔记、问答、练习和错题记录连接起来。
>
> 系统分为前端、后端、资料处理、检索和 Agent 执行几部分。前端是 Vue 3 和 TypeScript，后端是 FastAPI。SQLite 保存课程、原文位置、会话和练习状态，Chroma 保存向量。聊天模型通过 pi-ai 桥接接入；资料和业务记录保存在本机，生成所需的文本和题图仍会发送到配置的模型服务。
>
> 上传后，程序按格式解析内容，对需要识别的图片使用本地 OCR 和公式识别，并保存 Block 和来源位置。检索时按 PPT/PDF 的页、Word 或文本的小节形成上下文单元，再拆成较短的向量片段。这样能用短片段召回，同时读回整页或小节，避免只取到标题、丢失正文和代码。
>
> 第一个难点是中文问题检索英文资料。现在我把关键词检索和多语言向量检索结合起来。关键词扩展复用课程复习笔记里的中文和英文术语，但英文原词需要在当前原文中存在；向量模型直接处理原始问题。两路排序用 RRF 融合，再按正文相关性重排。
>
> 第二个难点是综合问题，比如比较课件里的各种树或排序方法。普通 top-k 容易集中在少数主题上，所以我按相关主题和比较维度分别召回，合并时优先保留各主题的材料。重排模型需要给出原文引用，程序检查引用存在；上下文裁剪后还会重新核对这些引用是否留在最终提示中，缺项就继续补搜或明确说明。
>
> Agent 部分是有边界的工具循环。模型输出结构化计划，程序校验工具、参数和范围，执行后再把观察结果交回模型。普通聊天最多三次检索工具调用，复习空间每轮最多六次行动；它还保存行动轨迹和状态，避免失败后只能看到一个空答案。
>
> 最后，我用 30 例数据结构问题观察整个服务流程。已有运行中动作完成率为 93.3%，但逐题复核也发现了综合列举遗漏、范围误判、资料外补充违反指令和生题失败等问题。因此我的重点是把这些失败定位到检索、提示打包、规划或生成阶段，并实现对应修复。这个项目当前是本机单用户应用，后续还需要真人复核、独立题集和优化后的对照评测。

## 3. 一条请求的数据流：用例比模块名更好记

例子：用户选定 Trees I、II、III，输入“根据这几份课件列举并比较各种搜索树”。

```text
用户问题 + 当前课程 + 所选章节
        ↓
识别本次要求：列举 / 对比 / 仅用课程资料
        ↓
读取当前有效笔记的双语术语和标题层级
        ↓
确定相关子主题、比较维度，标记清单可能不完整
        ↓
每个主题分别进行关键词召回 + 向量召回
        ↓
RRF 合并排名，按原文单元去重
        ↓
模型重排，返回主题 / 维度 / 连续原文引用
        ↓
程序检查引用存在，检查缺项，有限补搜
        ↓
为各主题保留材料，按输入预算放入整页或原文段落
        ↓
再次检查裁剪后的引用和覆盖缺口
        ↓
生成回答，保存实际证据、检索诊断、行动轨迹与用量
```

这个例子不能承诺每次都覆盖所有树：笔记可能漏术语，OCR 可能漏内容，模型也可能漏写答案。系统保存缺项和实际提示内容，是为了定位这些问题。

### 模块与作用

| 部分 | 主要作用 | 你需要能解释的边界 |
| --- | --- | --- |
| Vue 3 / TypeScript | 资料、笔记、聊天、练习、来源预览 | 切换课程或会话时要防止旧请求覆盖新页面 |
| FastAPI | API、普通聊天流式响应、后台任务 | 当前后台任务不是分布式任务队列 |
| SQLite / SQLAlchemy | 原文结构、业务状态、历史记录 | WAL 有助于读写并存，不意味着可无限并发写 |
| FTS5 / BM25 | 精确术语、代码名称、双语别名召回 | 不能单独理解所有中文描述与英文概念 |
| Granite / ONNX Runtime | 本地多语言向量编码 | 模型 INT8，不意味着全系统无模型服务开销 |
| Chroma | 向量存储和近似最近邻查询 | 使用标准 cosine HNSW，不是自研索引算法 |
| 结构化规划 / 工具执行 | 根据观察决定检索、讲解、练习等动作 | 有白名单、参数限制、轮数限制和状态检查 |
| pi-ai 桥接 | 接入模型服务并传回输出、用量 | 这是调用适配，不能称为自己训练的模型 |

## 4. 最值得展开的三个技术难点

### 难点一：中文问题如何找到英文课件

**问题。** 用户问“堆排序为什么不稳定”，课件写的是 Heap Sort。仅按中文字面匹配难以命中；仅用向量检索又可能召回其他排序方法。

**当前做法。** 复习笔记生成时保留“中文（English）”术语，`CourseVocabulary.read()` 从当前课程版本、已完成的最新笔记读取对照，并检查英文术语确实出现在当前章节原文。关键词组包含对应中英文表达，Granite 向量路径仍接收原始问题。两路通过 RRF 融合。

**为什么这样做。** 精确名称和代码适合关键词，换一种说法的问题适合语义匹配。复用现有笔记避免每次检索额外调用模型翻译，也避免维护固定课程词表。

**边界。** 原词存在只能帮助确认词表定位，不能证明中文翻译和所有父子关系都正确；笔记内容不直接充当课程事实依据。没有有效笔记时保留原始问题的多语言召回，综合清单不能保证完整。

**面试短答：**

> 我把跨语言问题拆成语义匹配和术语对齐两个部分。多语言向量负责中文描述与英文内容的相似性，课程笔记里的双语对照帮助 BM25 找到精确术语。对照按课程和章节隔离，最终结论仍回到课程原文。

### 难点二：综合问题为什么不能只提高 top-k

**问题。** “比较各种排序方法”需要覆盖多个算法和多个维度。全局 top-k 可能返回很多快速排序页面，却漏掉其他算法；还有一些关键类型只出现在正文中。

**当前做法。** 根据有效笔记的术语与标题层级展开相关主题，提取比较维度，分别召回。候选合并按轮次从各主题池中取材料，用原文单元 ID 去重；重排检查正文，给出可校验引用。对缺项有限补搜，选取材料时先保留各主题代表，再补充细节。

**关键细节。** 重排阶段引用存在不代表生成阶段能看到它。`_pack_materials()` 按预算裁剪后重新计算 `supplied_coverage`，对应引用被删掉就恢复为缺项。

**边界。** 子主题计划可能有遗漏或错误，笔记层级不是经过验证的分类体系；有原文也不保证模型会完整作答。旧运行 ds20 就出现了最终提示已有多份排序课件，回答仍误认范围并漏写多数方法的情况。

**面试短答：**

> 综合问题需要先解决覆盖问题。我的做法是分主题召回、按主题保留材料，并用原文引用检查比较维度。提高 top-k 可以增加候选，但不能保证每个子主题都被召回，也不能保证证据裁剪后仍留在提示中。

### 难点三：Agent 失败后如何定位和限制重试

**问题。** 一次请求可能经过规划、检索、重排和生成，最后失败不能只归因于“模型没回答好”。

**已有案例。** ds27 没有课程依据时讲解反复被拦截，最后耗尽行动次数；ds30 要求两道新栈简答题，生成阶段反复因引用无效失败，没有交付题目。

**当前代码处理。** 成功执行后才将动作加入完成去重集合；课程限定请求由程序约束知识来源；缺少课程证据时可以给出明确的不足说明。生成提示中的引用统一映射为 `M0`、`M1` 等局部 ID，再映射回真实来源；校验失败最多额外修复一次，仍失败通过 `GenerationFailed` 终止重复生成。每次行动保存结果与轨迹。

**不要夸大。** 这些处理已存在于当前代码中，但本次没有运行它们，不能宣称已把失败率降到某个数值。

**面试短答：**

> 我把模型计划和业务执行分开。程序控制工具范围、重复动作和状态，失败信息回到观察中，方便修正；但生成校验已经进行过一次修复后仍失败，就停止本轮，避免规划器重新启动相同生成而无限消耗。行动轨迹可以区分检索没找到、证据没装入提示和生成校验失败。

## 5. 高频追问与回答

### Q1：它和普通的 RAG 问答有什么区别？

> RAG 是我的知识获取链路。Agent 在此基础上根据当前消息、已有证据和工具结果选择下一步动作，比如继续检索、讲解或按用户要求生成练习。程序执行这些动作并记录状态，所以它包含受控的多步执行流程。检索和状态管理仍由确定性代码完成。

可以补充：普通聊天和复习空间是两套相关入口，不要把两者的调用上限、来源策略和交互协议混在一起。

### Q2：你用了 ReAct、Plan-and-Solve 还是 Reflection？

> 当前实现接近“计划—工具执行—观察—再计划”的循环。模型返回 JSON 计划，程序检查并执行，再把观察交回模型。普通聊天复用了 HelloAgents 的 Tool 和 ToolRegistry，主循环由业务代码控制。复习空间则由自己的行动分支执行。我没有把三种范式都包装成已落地功能，也没有训练一个规划模型。

不要说“项目直接使用 HelloAgents 默认 ReActAgent 完成所有功能”。目前看到的关键实现是工具抽象与自建控制流程。

### Q3：为什么不做多 Agent？

> 当前主要难点是课程证据能否召回、是否进入最终提示、范围是否遵循，拆成更多 Agent 不会自动解决这些问题。我先让单个受控流程可诊断。后续若有确实能独立完成并行的任务，再比较收益与额外调用、同步成本。

简历中“了解 MCP、A2A”可以作为知识储备；当前项目不要说已实现 MCP 服务或 A2A 多智能体通信。

### Q4：为什么同时用 BM25 和向量？

> BM25 对名称、缩写和代码符号有优势，向量更适合语义表达与跨语言匹配。它们的漏检情况不同，所以我同时保留两路候选。模型重排再判断正文能否支持当前问题，避免只因出现术语就当作有效证据。

### Q5：BM25 原理是什么？项目怎么处理中英文？

> BM25 综合词频、逆文档频率和文档长度归一化，词频贡献有饱和效果。项目的上下文单元索引中，英文按词处理，中文使用相邻双字片段，并编码为 FTS5 可处理的 token；双语术语对照会扩展查询组。FTS5 负责候选筛选和 BM25 排序，随后还有精确词法评分。

源码中 `ORDER BY bm25(...)` 使用 SQLite 的排序约定，分数更小排在前面，不要口头套成所有实现都“分数越大越好”。

### Q6：为什么用 RRF？参数是什么？

> BM25 与余弦相似度的分数尺度不同，直接相加不稳妥。RRF 按排名融合：某个候选在第 r 名时贡献 `1/(k+r)`，知识页/小节路径里 k 是 60，两路等权。两路都靠前的候选得分更高。它丢弃了原始分数差距，但避免依赖分数尺度校准。

小例子：A 在两路均排第 1，得分 `2/61`；B 只在一路排第 1，得分 `1/61`。不要把 RRF 得分解释为“答案正确概率”。旧 chunk 路径还有不同权重，讲代码时先说明当前讨论的是哪条路径。

### Q7：Granite 为什么适合？为什么用 INT8？

> 我的目标是 Windows 本机 CPU 使用，且课程有英文和代码，所以采用多语言模型，并保留 ONNX 部署。当前使用 Granite 311M 的 INT8 文件，运行器按官方 tokenizer、CLS pooling 和 L2 归一化输出 768 维向量。INT8 有助于控制模型文件和部署成本，但项目内质量、延迟和内存收益需要真实对照数据支持。

项目单次编码仍限制 512 tokens、批次 8 条，不因模型支持长上下文就把整份课件直接编码。不要说“已证明 INT8 完全无精度损失”，也不要把 INT8 写成 FP8。

### Q8：更换 Embedding 只改配置行不行？

> 不行。需要对齐模型结构、tokenizer、pooling、输出维度和归一化，而且不同模型的向量不能混在同一个索引里比较。项目记录模型和运行方式标识，发现不兼容就阻止使用旧向量；从已保存的原文重建到新索引目录，检查持久化和数量后再更新当前目录与模型标识。

重建失败保留旧目录和原文，不代表旧模型已经能够自动恢复服务。相似度阈值也不能直接沿用：当前 Granite 默认未启用旧的固定过滤门槛，仍需要质量校准。

### Q9：Chroma 底层是什么？为什么选它？

> 当前 collection 配置使用 cosine 距离的 HNSW。HNSW 通过分层邻近图进行近似最近邻搜索。Chroma 提供本地持久化、元数据过滤和向量查询，适合目前的单用户规模。我的工作主要在原文组织、混合检索、范围过滤和证据覆盖，没有自研 HNSW。

要能解释：近似检索可能漏掉真正近邻；没有项目级索引性能对比时，不声称它比其他向量库快多少。

### Q10：为什么有 Block、Chunk、RetrievalUnit 和 Passage？

> Block 保留原始内容结构和来源位置；Chunk 是较早的短片段检索层；RetrievalUnit 将同页或同小节相关 Block 组织起来；Passage 是该单元内适合向量编码的短片段。它们分别解决来源保真、短文本检索和上下文连贯问题。向量命中 Passage 后可以回到所属 Unit 的原文。

当前上下文向量片段通常不超过约 300 tokens，并给标题、文件名留空间；这与最终生成模型的输入预算是两件事。

### Q11：如何选择 chunk 大小和 overlap？

> 先满足编码器窗口约束，再尽量沿段落和句子切分，保留一定重叠。片段太短可能缺条件，太长会稀释主题并增加编码成本。项目使用实际 embedding tokenizer 计数，并保持切片来自原始字符串；没有 tokenizer 的回退是字符计数，不把它说成真实 token 数。

当前参数是实现选择，不是已经证明最优的值；合理的比较需要相同语料和题集下看覆盖、检索成本与最终答案。

### Q12：LLM 重排和普通向量排序差在哪？

> 向量先找整体语义接近的候选，重排模型则看到当前问题和候选正文，判断该正文是否直接支持问题。综合问题还要求按主题与维度返回原文引用。程序检查候选 ID、分数、主题范围及引用存在。重排失败会保留混合候选并标记回退，不能把未完成评估的覆盖当成已确认。

当前用配置的聊天模型做结构化重排，不要说部署了一个专门训练的 cross-encoder。

### Q13：引用校验能消除幻觉吗？

> 不能。程序可以检查引用是否真实存在、是否来自本次候选、是否留在最终提示中，但无法仅凭字符串证明引用语义支持结论。还可能有原文识别错误、推导错误或模型忽略证据。因此我把引用存在、课程证据支持和答案正确性分开评估。

可举 ds14：回答总体删除思路正确，却把查找右子树最小节点说成一直向右，自动辅助评分没发现；这说明高分与真实正确性不能画等号。

### Q14：怎样控制上下文窗口？

> 用模型配置的窗口减去输出预算和消息开销，得到输入预算。优先保留当前问题和各主题关键证据，整页放不下时选取原文段落，并记录省略。裁剪后再次核对引用和维度。这里用的是保守 token 估计，不是服务商精确 tokenizer；实际消耗以服务商返回用量为准。

`InputBudget` 当前对 CJK 和非 CJK 分别估计，不能把估计值称为真实计费用量。

### Q15：你做了哪些 Token 优化？

> 双语对照从现有笔记本地读取，避免查询时单独翻译；重排按来源缓存已校验的结果，缓存键包括请求、范围、课程版本、模型配置和原文摘录；规划器主要接收证据摘要，避免反复传整段原文。满足严格条件时还可以检索后直接讲解，省一次规划调用。

缓存仅在后端进程内，最多 4096 条；失败和未评估的候选不缓存。当前代码有这些措施，节省比例还不能用旧运行报告推算。

### Q16：学习记忆怎么做？为什么不把历史全塞进去？

> 保存近期消息、会话摘要、明确的长期讲解偏好和课程学习事件。近期对话帮助解析“它”“这题”等指代，摘要帮助接续早期话题，偏好调整详略与讲法。记忆不充当知识证据，也不能覆盖当前用户要求。作答记录还区分看过答案、用过提示和模型判题，避免把这些都解释为独立掌握。

后台记忆更新提交前检查版本和删除状态，避免较早的模型结果覆盖新状态。

### Q17：如何防止文档中的提示注入？

> 课程原文、题干、历史和记忆都作为数据处理，提示中明确不执行里面的工具或角色指令。程序层面用工具白名单，课程 ID 由服务绑定，章节范围和参数再校验，模型不能凭文本获得任意文件或命令权限。这能限制执行范围，但不能宣称已经彻底解决所有提示注入问题。

### Q18：SSE 为什么合适？和后台任务是什么关系？

> 普通问答需要服务端向前端持续发送状态和文本增量，单向 SSE 足够。FastAPI 返回事件流，前端使用 fetch 的读取流解析事件，处理 UTF-8 跨块、不同换行和多行 data。复习空间是另一个入口：提交返回 202，后台执行并保存状态，前端读取状态。不能把所有功能都说成 SSE。

当前后台任务在本进程中，持久化业务进度有助于恢复状态，但不是分布式队列，也不保证机器重启后任意任务自动继续执行。

### Q19：如何防止重复请求和旧状态覆盖？

> 后端按会话或任务设置锁，部分修改接口要求 revision，执行过程中检查取消标记和课程版本。前端使用会话切换序号、请求归属和草稿版本，旧结果返回时先检查是否仍属于当前页面。SQLite 开启 WAL，但长时间模型调用不应被理解为持有数据库事务完成全部流程。

不要把锁和 revision 合在一句“实现高并发”里：当前目标是单用户本机的状态一致性。

### Q20：文档解析支持哪些？公式为什么用独立进程？

> 按格式使用 PDF、DOCX、PPTX 解析库，旧 Office 格式接入 Tika，图片使用 RapidOCR 和公式识别。解析结果保留页码、幻灯片、段落、表格等来源位置，Word 不编造物理页码。公式识别放在独立环境和进程中，避免依赖与主后端环境相互影响。

图表、旧公式和低置信 OCR 仍可能不完整，“支持格式”不能等于“所有内容都准确识别”。当前项目没有采用 Docling 作为默认解析链路。

### Q21：生成笔记是不是对全文做一次 RAG？

> 笔记和问答目标不同。问答按当前问题检索，笔记需要按固定资料快照分批读取章节原文，再合并结果，防止只总结少数 top-k 片段。笔记记录课程版本和章节结果，后续术语扩展复用有效版本，资料变化后旧笔记不能自动代表新内容。

### Q22：怎么保证题目和答案匹配？

> 题目命中答案文件不代表对应关系成立。同一题号或同一年也不够，需要核对题干、选项等信息，保留 uploaded、embedded、model 等答案来源。模型生成参考答案不能称为上传标准答案。当前选择题按已有依据比较选项，其他题型主要由用户对照答案判断，不宣称实现所有题型的可靠自动批改。

### Q23：如何评测？30 题是否够？

> 这 30 例是基于当前课程的诊断集，包含知识、跨语言、代码、综合比较、资料外问题和流程场景。评测读取现有数据库的一致性副本，在隔离目录重建索引，保存课程、题集、代码和配置等版本信息。分别统计动作完成、标注原文是否进入提示和回答判定。它能定位当前失败，规模不足以证明跨课程泛化，也没有构成完整消融实验。

要能区分：8 道知识题、5 道跨语言、5 道代码、5 道综合比较、5 道资料外题、2 个流程案例。30 例包含多轮或出题流程，不全是相互独立的单轮问答。

### Q24：93.3% 怎么算？83.3% 和 66.7% 又是什么？

> 93.3% 是 28/30 例符合流程要求，不能证明答案正确。83.3% 是 AI 逐题复核后的 25/30 核心回答通过，尚未经独立真人确认。66.7% 是 32/48 个标注参考片段进入最终提示，分母是片段而不是题目，而且允许存在未标注的等价出处。这三个指标不能相互替代。

如果被问“为什么没达到 92%”，先说 92% 缺少可核对的对应对照，当前采用已有报告明确支持的口径，避免临场拼出一个分母。

### Q25：当前最大不足是什么？下一步做什么？

> 综合问题的范围和最终答案覆盖仍然是主要风险，资料限定请求也需要严格遵守；检索正确不意味着回答不会遗漏。已有评测还显示多次规划和重排会带来较高消耗。我会先针对具体失败做同条件的修改后评测，再补独立题集和真人复核，确认质量与开销变化。当前不优先扩展多 Agent 或公网多用户架构。

区分“下一步计划”和“已完成”：新题集、真人盲评、性能对照都不能写成已有结果。

### Q26：这是你独立写的吗？有没有使用 AI？

这题必须按实际贡献回答。不要把整份生成代码都说成手写，也不要把自己的工作只说成“调用工具”。可以用以下骨架，自行删去不符合实际的内容：

> 这是我的个人项目，我使用了 AI 辅助开发。需求、场景选择和复习中的问题来自我的实际使用；我参与了【你确实承担的设计、实现、调试或评测工作】。我可以从一次具体请求解释数据怎样进入系统、证据怎样被选取，以及为什么出现某类失败。AI 辅助产生的代码，我也需要逐步理解其边界，不能把没验证过的效果当成成果。

准备一个你真正能独立画出、修改并解释的模块，例如 RRF 融合、上下文预算或来源映射。个人贡献、开发时长、资料量、真实使用人数如果没有记录，不要现场编造。

## 6. “最有挑战的事情”怎样讲

按“出现了什么问题 → 怎么定位 → 改了什么 → 有什么结果和边界”讲，避免只列技术名词。

### 故事 A：综合排序问题遗漏

> 我发现系统对单个知识点解释比较自然，但在比较多个排序算法时会遗漏。查已有诊断记录后，我看到有时最终提示已经包含多个排序课件，回答却把范围误认为某一份文件，因此不能只靠增加召回数量解决。我把子主题覆盖、原文引用覆盖和最终回答的范围遵循分开处理：分主题召回，优先保留各主题材料，裁剪后重新检查引用，同时收紧范围提示。当前代码已有这些处理，但修改后效果还要通过同条件评测确认。

### 故事 B：动作完成却不等于答案正确

> 最初一个流程正常结束，很容易被算作成功。逐题复核时发现，BST 删除的回答总体方向正确，却把寻找右子树最小值的路径讲反了，而自动辅助评分给了高分。这让我把动作完成、证据存在和答案正确拆开统计，同时保留完整回答和实际证据供复核。项目的价值之一是能解释哪里失败，而不是只给一个总体分数。

### 故事 C：生题引用导致循环失败

> 有一次用户要求两道新简答题，模型生成引用无法映射到本轮材料，程序校验失败后规划器又重复生成，最后仍没有交付。我在当前实现中统一了提示中的局部引用 ID，校验时映射回真实来源，并将修复限制为一次，失败后终止重复生成。这样做的目标是让引用关系明确、失败可诊断；是否提高真实交付率还需要新运行验证。

选其中一到两个你最熟悉的讲。讲“做了哪些控制”必须能定位到代码，讲“提升了多少”必须能拿出运行对照。

## 8. 现场演示可以准备的四个场景

这是用户自行准备的演示提纲，本次没有运行。面试前先挑你已实际使用过、能稳定说明结果的例子。

2. **综合覆盖**：限定几份课件比较搜索树，说明为什么选择此范围，并展示缺项或原文定位。
3. **学习流程**：讲解一个概念后要求两道指定题型的题，展示题目、作答记录及答案来源；如果当前不稳定，不承诺现场一定完成。
4. **证据边界**：明确“仅根据课件”问一个资料外问题，观察是否说明依据不足，解释“未命中”和“课程完全没有”的区别。
